# SELinux distribution catalogs

## What catalogs are

Immutable SECentral SELinux distribution references for their declared platform,
policy and supported families. SECentral observes and normalizes facts from a
configured system; the catalog JSON is the authoritative record of those observed
reference facts, including platform, policy/packages, collector semantics,
collection metadata and family contents. The JSON artifact is the shareable unit;
`content_digest` identifies canonical semantic catalog content, not its sidecar,
acquisition metadata or database representation. Current schema 1 / collector
semantics V3 provides complete Boolean and port families.

## Structure

```text
catalogs/
  README.md
  LICENSES/GPL-2.0-or-later.txt
  <distribution>/<major-version>/<policy-type>/
    <content-sha256>.json
    <content-sha256>.review.json
```

Only reviewed, supported distributed artifacts belong here. Development candidates
stay outside this tree. This source rule is separate from database active/archive
lifecycle; directory names are navigation, not mutable revision identity.

## Review record

Each artifact has an adjacent compact SECentral review record identifying the
artifact digest, review date/scope and known interpretation limits:

```json
{
  "review_record_version": 1,
  "content_digest": "sha256:<content-sha256>",
  "review": { "date": "YYYY-MM-DD", "scope": ["booleans", "ports"] },
  "known_limitations": ["Product-relevant interpretation limits"]
}
```

`<digest>.review.json` refers only to adjacent `<digest>.json`; their filenames,
sidecar digest and validated artifact content digest must agree. Source-tree
presence means supported; no separate support state or artifact path is stored.
Review scope is nonempty and names only families supported by the artifact/product.
It means SECentral reviewed that artifact for use as a distribution reference for
the stated families, not a complete SELinux policy review.

The sidecar does not repeat observed platform/policy/package/collection facts or
require upstream repositories, source tags or revisions that may not be observable
from the system. First-artifact source/licensing research and acceptance reasoning
belong in development acceptance documentation, not the distributed review contract.

Review covers the bounded reference purpose and public-safe artifact contents.
The source envelope retains only `collected_at` and `collector_version` metadata.
Keep internal hosts, paths, database IDs, acceptance history and review-process
narration out of both artifact and sidecar. Never alter digest-bound semantic
content to hide private information; keep such a candidate internal instead.

## Trust

Supported means **SECentral-reviewed distribution reference for the declared
platform/policy and supported families**. It does not mean vendor-certified,
official vendor output, exact reconstructed vendor build or complete SELinux state.
Content integrity, SECentral review and publisher authenticity are distinct.

Obtain files from a trusted repository and pin a Git commit containing the artifact,
sidecar and licensing material. A mutable branch/latest link is not a pin; a digest
alone does not authenticate the publisher. The containing revision is pinned
outside the files, avoiding a self-referential commit field.

## Import

Manual/offline transfer is supported. Copy the reviewed files unchanged and use
**Catalogs → Import catalog → Preview → Confirm**, or run inside the Rails container:

```sh
bundle exec rake 'secentral:catalog:validate[/path/to/catalog.json]'
bundle exec rake 'secentral:catalog:import[/path/to/catalog.json]'
```

Compare the resulting content digest with the sidecar. Import validation does not
establish publisher trust or retroactively authenticate earlier imports.
See the [operator workflow](../docs/catalog-lifecycle.md) for import comparison,
reference selection and archive behavior.

## Updates and automatic updates

An optional exact compiled-policy companion is attached separately through
[local administrative tooling](../docs/catalog-policy-companions.md). It does not
change JSON/content identity or the review sidecar. JSON-only catalogs remain valid;
missing companion means unavailable future effective-policy facts, not empty facts.
Binaries are operator-supplied offline and stored in the existing database, not
added to this Git source tree or fetched automatically.

An update is a new reviewed, complete immutable artifact, imported explicitly.
Old revisions/raw import evidence remain; archive choices are separate actions.
New automatic reference selection can change or become ambiguous; explicit
revision-ID references continue naming their original revision.

There are **no automatic catalog updates**. Startup, migrations, image changes
and upgrades do not fetch, import, replace or activate catalogs.

## How to add another catalog

Collect from a system prepared as a distribution reference and passing the
collector's required cleanliness checks → validate → review the artifact for its
bounded reference purpose and public contents → add digest-named artifact and
minimal review sidecar → run:

```sh
bundle exec rake secentral:catalog:verify_distribution
```

The offline verifier checks sidecar version, adjacency, path/symlink confinement,
filename/content identity, artifact layout against its observed platform/policy,
authoritative artifact validation, portable metadata, review date/family scope,
limitations and orphan files. Both JSON parsers reject duplicate keys. The generic
verifier permits an empty temporary tree; the repository CI task additionally
requires at least one valid distributed artifact, without fixing its count or
distribution. It does not contact upstream, require source archaeology, reproduce
source, adjudicate licenses or certify vendor authenticity. Adding another
distribution or major version normally requires only artifact/review files.
